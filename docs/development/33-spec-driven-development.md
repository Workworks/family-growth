# Spec 驱动开发指南

## 1. 什么是 Spec 开发

Spec 是写代码前先明确“解决什么、哪些不做、怎样证明完成”的可验收契约。本仓库强制遵循：

```text
用户需求 → 需求账本 → Spec → 设计与工作包 → 实现 → 自动化验证 → 真实环境验收 → 证据与限制回填
```

页面存在、接口返回 200、测试替身成功或 APK 构建通过都不能单独证明需求完成；只有完成标准逐条取得对应层级证据，Stage 才能收口。

## 2. 每份 Spec 的最小结构

### 目标

描述用户可观察结果，而不是“新增接口”“优化代码”等开发动作。

### 边界

写清范围内、范围外、外部前置、安全不变量和不兼容决策。GitHub 仓库、签名证书、PostgreSQL、Android 设备等不能被静默假设为已具备。

### 验证方式

为每条能力指定环境、操作、预期和证据，至少区分静态契约、自动化、目标数据库、安装态、真机/平板和端到端验收；低层测试不能代替高层闭环。

### 完成标准

使用编号、可判定的 `PASS / FAIL / BLOCKED` 条目。未执行不得写 PASS；外部条件缺失写 BLOCKED，并进入 `docs/BLOCKERS.md`。

## 3. 推荐模板

```markdown
# <Stage N：需求名称>

状态：NOT_STARTED | IN_PROGRESS | COMPLETED | BLOCKED
产品 Phase：...
需求：REQ-...

## 目标与非目标
## 边界与不变量
## 工作包
| ID | 状态 | 内容 |
## 数据、API、Android、部署与文档变化
## 验证方式
| ID | 环境 | 操作 | 预期 | 证据 |
## 完成标准
- [ ] AC-N-01 ...
## 安全检查、已知限制与交接
```

## 4. 落地规则

- 新增功能、跨模块修复、界面重构、发布、部署或治理变化必须先有 Spec。
- 规格要点并入同号 Stage 报告，避免第二份状态真相；跨 Stage 验收放 `acceptance/`，架构放 `design/`。
- 新需求先进入需求账本，再由 Spec 引用；不得用 TODO 替代长期需求历史。
- API、数据库、安装、界面或配置变化同步设计、OpenAPI、手册、测试和运行说明。
- 验收发现缺陷先记 `bug/bugList.md`，环境阻塞写 `BLOCKERS.md`。
- `COMPLETED` 需要真实产物、命令、退出码、测试与证据；缺仓库、设备、证书或外部账号时保持 `BLOCKED`。

## 5. 纯文档和只读任务

只读咨询、拼写修正、格式整理和不改变行为的机械修改可复用现有 Spec。文档治理改变事实源、目录职责或 Agent 执行协议时仍需独立 Stage，因为它会影响所有后续任务。
